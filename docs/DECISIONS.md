# Decisions log

Format: **ADR-NNN — Title** (date). Context → Decision → Consequences.

## ADR-001 — Ollama over LM Studio (2026-09-09)
- **Context:** Need a local lightweight tool-calling brain; LM Studio felt like extra GUI fluff.
- **Decision:** Use **Ollama** CLI/API as the only local runtime for v0.
- **Consequences:** Simpler headless ops; pull a small instruct+tools model (≤3B preferred on this VM historically; RAM is now ~15 GiB so 3B–7B is plausible — start 3B, document).

## ADR-002 — Overlay = local web UI in Hyprland float (2026-09-09)
- **Context:** Need something easy to ship and maintain as the *main* input surface.
- **Decision:** Small localhost web UI (HTML/JS or minimal Vite) shown as a centered floating Hyprland window with windowrules; not GTK-first for v0.
- **Consequences:** Fast UI iteration; must add solid `windowrulev2` and a single-instance toggle. Can later swap shell without rewriting tools.

## ADR-003 — Keybinds as data + composed skills (2026-09-09)
- **Context:** Fear of rewriting rules when expanding beyond workspaces.
- **Decision:** Ship `run_binding` fed by `omarchy menu keybindings --print` from day one, plus a few composed tools/skills (`scratch_toggle`, `open_planning`).
- **Consequences:** Model never owns chord strings; catalog stays in sync with Omarchy updates.

## ADR-004 — Confirm before saving skills (2026-09-09)
- **Context:** Cloud/agents may draft automation; user wants control.
- **Decision:** Skill drafts land in `skills/drafts/`; promote to `skills/` only after explicit user OK.
- **Consequences:** UI/CLI must support propose → show diff → confirm.

## ADR-005 — Thought bubbles → live console (2026-09-09)
- **Context:** Debugging agent thoughts; file-only logs are weak.
- **Decision:** Use `omarchy-notification-send` with `--exec` launching a **live** console (tail -F / streaming) for that run id.
- **Consequences:** Each run gets `logs/runs/<id>.log`; console attaches to the stream.

## ADR-006 — Google Calendar vs stock “Calendar” binding (2026-09-09)
- **Context:** User’s planning stack includes Google Calendar. Stock **SUPER + SHIFT + C** opens HEY calendar; **SUPER + CTRL + ALT + D** toggles Omarchy clock shell, not Google Calendar.
- **Decision:** Planning skill opens Google Calendar via `omarchy-launch-or-focus-webapp` / `omarchy-launch-webapp https://calendar.google.com/` — do not call the HEY binding for “planning”.
- **Consequences:** Document clearly so agents don’t “fix” Calendar by simulating SUPER+SHIFT+C.

## ADR-007 — Host Lua dispatch and reviewed binding map (2026-09-09)
- **Context:** Live Hyprland 0.56 rejects legacy `hyprctl dispatch workspace ...`; `binds` contains opaque `__lua` callbacks, and catalog output has no command column.
- **Decision:** Use the installed Omarchy Lua expressions (`hl.dsp.focus`, `hl.dsp.window.move`, `hl.dsp.workspace.toggle_special`). Refresh the catalog before resolving an exact chord/description; execute reviewed scratch, Outlook, WhatsApp and numbered-workspace mappings only.
- **Consequences:** Unsupported bindings fail explicitly. Never execute arbitrary Lua callback IDs or model-generated shell. Syntax references: installed `/usr/share/omarchy/default/hypr/bindings/tiling.lua` and https://wiki.hypr.land/Configuring/Basics/Window-Rules/.

## ADR-008 — Workspace placement and launcher safety (2026-09-09)
- **Context:** Focus helpers can jump back to another workspace; the packaged focus wrapper constructs a shell command with eval. The current default browser is Brave despite Chromium being present.
- **Decision:** Reuse a matching app window or launch via the argv-safe `omarchy-launch-webapp`; move each verified window address to the lowest unused positive numbered workspace for planning. Read literal personal Outlook/WhatsApp URLs from bindings.lua.
- **Consequences:** Planning consolidates existing app windows. App identity and final workspace are checked; timeouts return partial progress. No new browser profile is used for the account webapps.

## ADR-009 — Strict JSON plans after failed native tool-call demos (2026-09-09)
- **Context:** qwen2.5:3b native tool calling created only a workspace for the planning request and falsely claimed completion. It also composed scratch_move_here with the full scratch-and-mail recipe, duplicating a mutation.
- **Decision:** Default to Ollama `/api/chat` structured output with a strict action-plan schema and concrete recipe examples. Validate the entire plan before executing any action, reject duplicate calls and recipe/action mixtures, and derive completion messages from successful tool results. Keep the bounded native tools loop opt-in (`JARVIS_PLANNER=tools`) for future model evaluation.
- **Consequences:** No regex prompt router or cloud runtime. Plans are local model output, executed through the same reviewed argv CLIs. End-to-end evidence must prove a new workspace and actual full recipe invocation, not trust model replies. See https://docs.ollama.com/capabilities/tool-calling and https://docs.ollama.com/capabilities/structured-outputs.

## ADR-010 — Local HTTP protection and focus capture (2026-09-09)
- **Context:** A localhost action API must not accept requests from unrelated web pages. The overlay steals focus from the user's intended scratchpad target.
- **Decision:** Bind only 127.0.0.1:7421; require a per-process token, exact Host and same Origin for mutations, no CORS, bounded request sizes, one active desktop run. Record the target address before opening the overlay, close the overlay before actions, and restore that target or fail if it disappeared.
- **Consequences:** The isolated Chromium overlay profile is runtime-only under ignored logs; account webapps keep the user's default browser profile. Escape and toggling close only the Jarvis overlay. Notifications carry action summaries/results, never private model reasoning.

## ADR-011 — One typed action per v0 request (2026-09-09)
- **Context:** An unconstrained JSON actions list still made qwen2.5:3b combine a scratch action with its full recipe. A workspace test also emitted a string instead of an integer.
- **Decision:** Constrain structured generation with per-tool argument schemas and at most one action; compound workflows use a complete approved skill. Invalid plans fail before any desktop mutation.
- **Consequences:** Both recipe variants and planning pass model evaluation. Arbitrary multi-action composition is deferred; extend by adding reviewed recipes. Completion text comes from successful actions rather than model claims.

## ADR-012 — M4 CLI stub and explicit approval (2026-09-09)
- **Context:** M0–M3 includes a usable but limited confirm-before-save path.
- **Decision:** A local CLI copies candidates into drafts, shows complete file diffs, and promotes only an explicitly approved SHA-256 digest. Changes invalidate that digest; existing installations cannot be overwritten. Promoted scripts remain CLI-only.
- **Consequences:** The two requested example skills are preapproved by the implementation request. Future recipes require user approval; no model tool can promote drafts. M4 UI/discovery remains open in issue #5.

## ADR-013 — Chromium app identity on repeat launches (2026-09-09)
- **Context:** `--class=jarvis-overlay` was honored on first launch, but Chromium changed subsequent app windows to a URL-derived class even after restarting its dedicated profile. Tests caught tiled duplicate windows.
- **Decision:** Serve the overlay at the unique `/jarvis-overlay` route. Match both the requested class and Chromium's observed `chrome-127.0.0.1__jarvis-overlay-Default` in window rules, focus tracking and single-instance checks. Keep the dedicated profile and disable extensions; do not kill browser processes as part of normal toggling.
- **Consequences:** Actual browser class differs from the handoff's suggested literal on repeat launches. Matching the stable app identity preserves floating, centering, Escape, focus restoration and single-instance behavior without depending on Chromium honoring a flag.

## ADR-014 — Approve-before-execute transparency pass (2026-09-09)
- **Context:** v0 executed tools immediately after planning; the overlay only showed "Thinking…" then a final reply, so the user could not see or stop a mutating action before it ran. User feedback asked for **see + control**: visible plan/tool IO and no desktop mutation without explicit Run.
- **Decision:** Every prompt now runs in two phases. `POST /v1/run` only plans (JSON planner, or the first tool-call turn under the opt-in `JARVIS_PLANNER=tools` loop) and returns `status=awaiting_approval` with the proposed `plan` when it has actions; chitchat with zero actions still finishes immediately with `status=done` (no approval step). `POST /v1/runs/<id>/approve` executes the stored plan; `POST /v1/runs/<id>/deny` cancels with no side effects. `GET /v1/runs/<id>` now returns `status | plan | steps[] | reply` so the overlay can render a live per-tool step list during execution. A run held `awaiting_approval` for more than `AWAIT_TIMEOUT` (900s) auto-denies and releases the single-run lock so an abandoned overlay can't wedge the brain. Approve/deny is per-run, not per-step (`approve_step` from the design doc is deferred — the JSON planner already caps a plan at one action/one complete recipe, so run-level approval already gives step-level granularity in practice; add `approve_step` only if plans grow beyond one action).
- **Consequences:** `execute_json_run`/`execute_run` were replaced by `plan_and_maybe_run`/`execute_plan` (JSON planner) and `plan_tools_run`/`execute_tools_plan` (opt-in tools loop), all gated by the same approve/deny/expiry code path so the experimental loop can't bypass control. The overlay grew a plan checklist, live step list, Run/Cancel buttons, and an always-visible **Open console** button (see ADR-015). `scripts/demo-test.py` now approves/denies through the API instead of expecting immediate execution.

## ADR-015 — Config file location, notification/approval modes, and overlay size (2026-09-09)
- **Context:** The design doc asked for a config file (approval_mode, show_notifications) without a rebuild, and for the overlay to grow enough to show the plan/step UI plus an always-available console button.
- **Decision:** Config lives at `~/.config/jarvis/config.toml` (same convention as `~/.config/hypr/bindings.lua` — a per-user Omarchy dotfile, not repo-tracked), read once at server start via stdlib `tomllib`. Missing file or invalid `approval_mode` silently falls back to the safe default `"always"`. `approval_mode = "skills_trusted"` auto-runs a plan only when every action is `run_skill` (a reviewed recipe); anything else still awaits approval. `approval_mode = "off"` auto-runs everything, logs a warning line to the run log, and the overlay footer shows "⚠ approval off". `show_notifications = false` keeps writing the run log but skips the desktop notification. The overlay window grew from 520×150 to **640×460** (`scripts/toggle-overlay.py` `--window-size`, the `o.window(...)` rule in `scripts/install-hotkey.py`, and the matching assertion in `scripts/verify-host.py`) to fit the plan checklist and step list. The **Open console** button is always rendered (never hidden), disabled only until a run id is known; the current run's id is written to the overlay's own `localStorage` as soon as `/v1/run` returns, so the button stays enabled — pointing at the current or most recent run — even across closing and reopening the overlay window (a fresh page load each time). Escape both denies any run still `awaiting_approval` and closes the overlay, so it can never leave an orphaned pending run.
- **Consequences:** New endpoint `POST /v1/runs/<id>/console` spawns `console/jarvis-console <id>` server-side (same validated argv pattern as the existing notification `--exec`), since browser JS cannot exec a process itself. `GET /health` now also reports `ollama: ok|fail` and `approval_mode` for the overlay footer. Verified live on this host: plan/approve/execute, deny-then-nothing-happened, and Open console re-enabling on overlay reopen after a service restart (see PROGRESS.md).

## ADR-016 — Self-improve loop: deterministic intake, not model-driven drafting (2026-09-09)
- **Context:** `docs/passes/active/CLAUDE_SELF_IMPROVE_PASS.md` asked for Jarvis to file rich bug/feature records with clarifying Q&A, a local backlog, and prepared (never auto-sent) handoffs to other agents — built on top of the plan → approve → execute control plane from ADR-014/015. The obvious approach would let the local Ollama model draft the issue title/body/questions itself, but ADR-009 already found qwen2.5:3b unreliable at freeform structured output (incomplete plans, false completion claims) even with a bounded single-action schema.
- **Decision:** Bug/feature intake is entirely deterministic, not model-driven. `POST /v1/run` detects intent via regex — `/report`/`/feature` slash prefixes, or natural-language triggers ("you messed up", "I wish it could…") — and `/backlog`, `/dispatch <issue> to <agent>`, entirely **outside** the JSON/tool-calling planner. A fixed 3-question script per kind (bug: expected/actual/repro; feature: what/why/constraints) is asked one at a time via new `status=awaiting_answer` run state and `POST /v1/runs/<id>/answer` (reply `"skip"` to stop early). The server itself gathers the context pack (last run's plan/approval/log tail; a live `hyprctl clients/workspaces` snapshot and `catalog_bindings` query, each only when the seed text looks window/binding-related, to avoid dumping irrelevant desktop state into every issue) and fills `docs/templates/ISSUE_BUG.md` / `ISSUE_FEATURE.md`. `report_bug`/`report_feature` are excluded from both the JSON planner's `PLAN_SCHEMA` and the tool-calling loop's tool list (`LLM_EXCLUDED_TOOLS`) — the model never sees them, so it can't hallucinate a filed issue's content. The finished draft becomes an ordinary one-action plan (`report_bug`/`report_feature`) and goes through the **same** approve/deny/expiry path as every other tool call (reusing a new `commit_plan` helper factored out of `plan_and_maybe_run`); the overlay shows the full title+body as a `draft` preview before Run. `report_bug`/`report_feature`/`list_backlog`/`prepare_handoff` are also exempted from `execute_plan`'s `restore_target` (no desktop window to restore for filing an issue or writing a local file). Redaction (`core.redact`, extended with `sk-`/`gh[ops]_` token patterns) is applied both when the server assembles the draft and again inside the `report_bug`/`report_feature`/`prepare_handoff` actions themselves, so direct CLI/skill use (e.g. `report-last-failure`) is never unredacted just because it skipped the server's intake path.
- **Consequences:** Filing is slower to build (a fixed script, not a smart assistant) but predictable and testable without a live model call — `SelfImproveServerTest`/`BacklogActionsTest` cover intent detection, the Q&A state machine, redaction, and template filling with mocks only. `gh issue create --label` fails outright if a label doesn't exist yet in the repo; `report_record` now calls `gh label create --force` (idempotent create-or-update) for its four labels (`bug`, `jarvis-reported`, `enhancement`, `backlog`) immediately before creating the real issue — discovered live on this host on the first real filing attempt (see PROGRESS.md). Dispatch is prepare-only by design: `prepare_handoff` writes `docs/backlog/handoffs/issue-<n>-<agent>.md` and never calls any agent API — no real-send hook exists in this pass at all, for any agent (a non-goal per the source doc); `docs/backlog/README.md` documents `dispatch.enabled = false`-by-default as the convention a future hook would have to follow, not a key the code reads today.

## ADR-017 — Agent front door, scope and disposable briefs (2026-09-09)
- **Context:** Multiple historical passes and prompts (`ASTRA_HANDOFF`, `CLAUDE_*_PASS`, `PROMPT_*`) made it ambiguous which doc a cold agent should read first, or which brief was still current versus superseded. There was also no shared convention for which files two agents could touch in parallel without colliding.
- **Decision:** `START.md` is the front door — first lines say to read it fully before any other doc or code — and owns job modes (fix issues / implement a pass / feature from backlog / explore-debug) and the Issue Loop; `AGENTS.md` is slimmed to durable invariants only, pointing at `START.md`. Passes and handoffs each get `{README,INDEX,active/,archive/}` with INDEX status `active | done | superseded`; a brief moves to `archive/` on merge/close and is never treated as current instructions once archived. Parallel work is scoped by `area:{overlay,brain,actions,skills,docs}` labels; `parallel-ok` requires explicit comma-separated `Allowed paths:`/`Forbidden paths:` in the issue body, `single-writer` is the default for `area:brain`/control-plane work, and `scripts/agent-status.py` (`ensure_labels`-style idempotent GH label list — `area:*`, `parallel-ok`, `single-writer` — created on this repo) parses those path lists to warn on overlapping scope or shared areas between open issues.
- **Consequences:** Existing `docs/ASTRA_HANDOFF.md`, `docs/CLAUDE_*_PASS.md` and `docs/PROMPT_*` files migrated into `docs/passes/{active,archive}/` with an `INDEX.md`; every cross-reference to their old paths (ADR-016, `docs/PROGRESS.md`) was updated rather than left dangling. `agent-status.py`'s collision/scope warnings are conservative prefix-overlap heuristics for human review, not an enforcement mechanism — they never block or auto-schedule anything, and area/parallel-ok labels coordinate but do not authorize spending or spawning other agents (unchanged from ADR-016's dispatch-is-prepare-only stance). Covered by `tests/test_journal.py::JournalTest.test_status_scope_collisions`.

## ADR-018 — Versioned run journal, debug-only module internals (2026-09-09)
- **Context:** `logs/runs/<run_id>.log` (ADR-005) was coarse free-text — useful for a live `tail -F` console but not a structured record an agent could `jq` for "what did the user ask, what did Jarvis decide, what actually happened, does anything look wrong." Per-tool argv/stdout spam at the same verbosity as user-facing events also made the log noisy for a human skimming it.
- **Decision:** `brain/journal.py` is the primary evidence: an append-only JSONL journal at `logs/journal/CURRENT.jsonl`, four bounded records per terminal run — `prompt → process → done → eval` — each carrying `ts`, `jarvis_version` (from `VERSION`), and `git_describe` (cached once at process startup, not shelled out per-run or per-poll). `evaluate()` is a local, synchronous, rule-only check (approved plan vs. executed steps; no subprocess, model, or desktop snapshot) that sets `flag: null|suspicious|mismatch|partial` — conservatively `suspicious` even on a fully successful run, since matching tool return codes can't independently prove the desktop actually changed. Each run's journal records are also appended to `logs/runs/<run_id>.log` unchanged, so the existing `jarvis-console`/notification `--exec` path keeps working against the same file, just now JSONL instead of prose. Module/internal detail (raw argv, poll noise) is `debug`-only via `log_level = "debug"` in `~/.config/jarvis/config.toml` (default `"info"`), written to `logs/debug/<run_id>.jsonl` instead of the journal. A `VERSION` file plus "change VERSION → restart → first journal write rotates `CURRENT.jsonl` to `logs/journal/archive/v<old>-<UTC timestamp>.jsonl`" is the version-reset procedure, so evidence from a since-changed code path stays attributable to the commit that produced it via `git_describe`.
- **Consequences:** No cloud LLM call and no extra subprocess/hyprctl snapshot on the eval path — flags are cheap heuristics for a human or agent to triage, never automatic GitHub issues (bug intake can still pull the flagged excerpt in if the user `/report`s). `GET /v1/runs` polling stays silent (no journal/debug write per poll). Journal/debug directories are gitignored, mode 0700/0600; code and schema (this ADR, `docs/LOGGING.md`) are the durable git-tracked record, not the runtime data itself. Verified live: a real "say hello" run produced the four phases with real `jarvis_version`/`git_describe` (the latter correctly `-dirty`-suffixed on an uncommitted tree), and a real approved `list_backlog` run's eval correctly flagged `suspicious` per the conservative-on-success rule (see PROGRESS.md). Covered by `tests/test_journal.py` (rotation, redaction/bounds, all four phases across six run outcomes, write-failure still releases the busy lock, debug opt-in).

## ADR-019 — Overlay stays open through execution instead of auto-closing on Run (2026-09-09)
- **Context:** ADR-010 closed the overlay window as part of `restore_target()`, called at the very *start* of `execute_plan`/`execute_tools_plan` — before any step ran or the overlay's own poller could render a single "Running …" line. The overlay's live step-list UI (ADR-014) was therefore effectively unreachable: pressing Run destroyed the window showing it within milliseconds. Worse, `restore_target()` then re-focused the *pre-overlay* window, which each action's own dispatch (`open_app`, workspace switches, `run_skill`) immediately re-focused past on completion — for a newly-launched webapp that can take up to ~30s (`open_app`'s launch-and-poll loop). Net effect, matching Alex's report: press Run, the overlay vanishes, the screen flashes to the old window, and the real result appears later with nothing visible signaling progress in between — "a flash then back to nowhere," not something that "feels permanent."
- **Decision:** `restore_target()` keeps focusing the pre-overlay target before an action runs (still required so `scratch_move_here`/current-window-dependent `run_binding` chords operate on the window the user meant, not the overlay) but no longer closes any window. The overlay now stays open for the whole run — planning, awaiting approval, executing with a live step list, and the terminal `done`/`error` reply — and is dismissed only by the user: **Esc** (`POST /v1/close`, unchanged) or pressing the hotkey again, which reuses `toggle-overlay.py`'s existing single-instance logic (close if the overlay is the focused window, otherwise just refocus it and refresh `overlay-target.json` to whatever's active now). Chitchat and denied plans were never affected either way — `commit_plan`'s zero-action branch and `handle_deny` never called `restore_target` in the first place.
- **Consequences:** The user can now actually watch a run's step list happen instead of losing the window an instant after pressing Run; a workspace switch or new app launch is visible around/behind the (640×460, not fullscreen) overlay rather than hidden behind an premature refocus. No new endpoint or client-side auto-close was added — deliberately minimal, since `toggle-overlay.py` already had correct single-instance open/close/refocus behavior that just wasn't being exercised as the run's dismissal path. If the overlay ever needs to auto-dismiss after a delay, that's a separate follow-up, not required by this fix. Covered by `tests/test_jarvis.py::BrainTest.test_restore_target_focuses_without_closing_overlay` (no `closewindow` dispatch, exactly one `focuswindow` call) and `test_restore_target_noop_without_a_target`.
